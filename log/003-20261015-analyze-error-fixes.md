## 目标

`/speckit-analyze` 报出 `NEEDS CHANGES`,四项 error 全部集中在两个空档:资源该落在哪一层、以及探针结论不成立时的出路。本轮只修 error 级,并把用户新增的"验证记录怎么归档"这一决定固化下来。

## 四项 error 的口径

1. **F-001 依赖 jar 与 `.gitignore` 冲突。** 原 `.gitignore` 里 `*.jar` 之后有一行 `!libs/*.jar` 白名单,意味着放进 `libs/` 的游戏本体 jar 与基础 mod jar **会被 git 跟踪**。决定:依赖 jar 放**顶层** `libs/`(符合宪法第八条"构建配置留顶层"),并**删掉那行白名单**,使 jar 一律不入库。放 `src` 里再靠白名单提交的方案被否决——那是分发风险。
2. **F-002 占位贴图无归属。** 决定:占位图放 `src/main/resources/placeholder/`,由 `src` 层**自己的** `.gitignore` 忽略;T037 的验收改为"占位图不出现在 `git ls-files` 输出中",可判定。"直接引用游戏本体目录"的方案被否决——缺图时游戏内表现异常,会污染后续验证结论。
3. **F-003 EC-008 的兜底与硬要求冲突。** plan 原来写"若两条路都不可行,缩减为只覆盖抽牌动作,并把限制记入规格边界情况",但 FR-012 与 EC-008 都不允许放宽。决定:**删掉缩减口径**,改为"若两条路都不可行,停止实现并回到 `/speckit-clarify` 重新界定 EC-008";T021 补上两条备选与停止条件,并把依赖改为 `T004, T020`(探针结论定方向)。
4. **F-004 验证记录没有落点。** 见下。

## 三层验证记录机制(本轮新增的项目级约定)

用户决定:可复现的**流程**写进 spec;验证过程产生的**记录**全部落入 `memory/log/`;只有经得起复用、对后续有约束力的**结论**才升入 `memory/facts/`,且 facts **严入**。

落地为三处:

- `memory/README.md` 新增"本项目的验证记录分三级"表,写明三级的门槛与位置;
- `plan.md` 的 Testing Strategy 改为:流程写本节,记录追加到 `memory/log/`,结论升入 `memory/facts/`,判定标准见 `memory/README.md`;
- `tasks.md` 新增 T040(逐次记录落盘)与 T041(机制定稿,并在证明通用后形成技能改进提案,**单独排期**)。

用户的附加约束:分类法若被证明通用,应作为 `agent-dev-memory` 的改进候选,但**技能本体在项目开发完成前不改动**。这与技能自身的"可扩展性"设计意图一致,不需要在技能里新增分类法。
