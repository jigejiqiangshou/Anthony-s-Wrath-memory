# agent-dev-memory 常驻改进提案

状态:草稿(T045);**技能本体在项目开发完成前不改动**
依据:`memory/log/004-20261015-warning-fixes.md`、`memory/log/check-artifacts.mjs`

## 为什么

本项目在两轮分析里各暴露了一类"靠读发现不了"的问题:

1. 我按通读报告"需求覆盖完整",机械核对当场抓出 `SC-004`、`EC-004`、`EC-005` **没有任何任务承接**。通读判断不出计数类事实。
2. 三层仓库里,`plan` 引用了不存在的任务号、任务编号出现空洞——这类引用完整性问题同样只能机械核对。

因此建议把"文档一致性核对"从"凭自觉"升级为**技能承认的常驻组件**:可复用、可声明豁免、有明确触发时机。

## 归属划分

| 部分 | 归属 | 理由 |
| :--- | :--- | :--- |
| 检查器本体(编号连续性、依赖完整性、需求承接、引用有效性、标签映射) | **技能包** | 与语言、框架、项目无关,纯结构 |
| 豁免名单(如「某需求按规格声明不安排验收」) | **项目侧声明** | 豁免必须带规格依据,不能由技能替项目决定 |
| 触发时机(改动 spec 层之后) | **技能约定** | 属于工作流,不属于工具 |
| 门槛(哪些检查项是硬门禁、哪些是告警) | **项目侧声明** | 与技能自身「不做项目专用硬门禁」的取舍一致 |

这条划分是本提案的关键:技能提供**机制**,项目提供**门槛与豁免**。技能不该替项目定验收标准。

## 建议改动(三处,均为增量)

1. **`scripts/check-artifacts.mjs`(新增)** —— 通用检查器,输入项目根与功能目录,输出 JSON;无第三方依赖,只用 Node 内置模块。以本项目已验证的版本为基准(见 `log/check-artifacts.mjs`)。
2. **`references/workflow.md`(追加一小节)** —— "何时必须核对结构":在检点五问之后补一条**机械核对**,写明适用条件(项目有 spec/plan/tasks 结构时)、放行判据(检查器 `ok: true`,或未通过项均有带依据的豁免)、以及报告口径(不得以通读代替核对)。
3. **`SKILL.md` 的 Light check(加一个勾选项)** —— "若项目声明了结构门禁,门禁已复跑且通过,或有带依据的豁免"。

不建议改的部分:四库语义、五问字段、索引协议、`coldStart` 上限。这些已经稳定,且与本提案无关。

## 需要项目侧配合的形式(SKILL.md 里的说明要定这个)

技能应要求项目在**绑定文件**(`AGENTS.md` 的 Agent memory 段)里声明两件事:

- 门禁脚本的**路径**(缺失即表示该项目未启用该检查器);
- 豁免名单的**声明位置**(通常就在门禁脚本内或紧邻的说明文件里)。

这样技能无需猜测项目结构,项目也不必改技能。

## 验收判据(提案自带回归验证)

1. **正例回归**:在 `specs/001-anthonys-wrath` 上运行检查器,结果应为 `ok: true`。这是本项目当前的实测状态(45 个任务、27 条需求、零问题)。
2. **负例回归(必须有,否则工具没被真正验证过)**:四种破坏各测一次,都必须被报出——
   - 删掉某条任务的 `SC-*` 标注 → 报"需求无任务承接"(本项目已实测通过一次);
   - 把某条 `depends:` 指向不存在的任务号 → 报依赖悬空;
   - 制造编号空洞或重复 → 报编号问题;
   - 在 `plan.md` 引用一个不存在的 `T\d{3}` → 报引用无效。
3. **豁免生效**:把豁免项从名单中移除,该需求应立刻被报为无承接——证明豁免是显式声明而非静默跳过(本项目已实测:移除 `EC-007` 豁免后立即报出)。
4. **环境错误**:参数缺失或功能目录不存在时,给出可读提示并以非零码退出,不得静默成功。

第 2、3 条是本提案的**准入门槛**:一个没被负例验证过的检查器,与没有检查器区别不大——本项目这一轮正是靠"故意破坏再看是否报出"才确认它真的在工作。

## 与三层验证记录机制的关系

两者互补,建议一并交付:

- **三层验证记录机制**(流程在 spec、记录在 log、结论严入 facts)管的是"验证结果写在哪";
- **门禁**管的是"文档结构有没有被改坏"。

前者是本项目已落地的约定(`memory/README.md`),是否升级为技能级通用能力,由 T041 定稿时判断——若证据不足,只交付门禁部分,不强行通用化。

## 已知不做的

- 不在技能里替项目决定检查项门槛;
- 不改技能原有结构(四库、五问、索引协议);
- 不引入第三方依赖或新的工具链(与技能"不引入 MCP、锁服务、第二套备份工具"的取舍一致);
- 不与 spec-kit 的 helper 合并——两者的职责边界不同,且 helper 属于另一个包。
